# Роли и полномочия

Документ описывает модель ролей, scope, иерархию управления и
матрицу прав. Всё описанное здесь реализовано в `apps/access`.

## Модель

```text
User ──< RoleAssignment >── (role, scope_type, scope_id, valid_until)
```

`RoleAssignment` — связь пользователя, роли и scope. Один пользователь
может иметь несколько назначений; права = **объединение**.

## Роли

| Роль | Что даёт | Кому выдаётся |
| --- | --- | --- |
| **SUPERVISOR** | Чтение всего (кроме секретов), управление ролями, приглашение ADMIN | Двое при bootstrap |
| **ADMIN** | Полный CRUD в домене, приглашение OPERATOR/VIEWER | SUPERVISOR |
| **OPERATOR** | Создание/отмена deployments, запуск конфигов | ADMIN |
| **AUDITOR** | Чтение аудита, отчётов, deployment-логов | SUPERVISOR |
| **VIEWER** | Чтение хостов, профилей, deployments (без аудита) | ADMIN |
| **SERVICE** | Машинный доступ (API), не имеет UI | SUPERVISOR (для сервис-аккаунтов) |

### Разница AUDITOR и VIEWER

- **VIEWER** видит конфигурацию парка (хосты, профили, деплои).
  Не видит аудит и чувствительные логи.
- **AUDITOR** видит аудит, отчёты, логи. Но не может менять конфиги.

Обе роли — read-only. AUDITOR выдаётся только SUPERVISOR'ом.

### SERVICE

Технический маркер, не выдаётся через `RoleAssignment`. Существует
для полноты модели; права определяются через `ServiceAccount.scope`
(см. `docs/service-accounts.md`).

## Scope

Помимо роли — область применения:

| Тип | Что покрывает |
| --- | --- |
| **GLOBAL** | Всё (только для SUPERVISOR) |
| **DOMAIN** | Один домен и всё внутри него (хосты, наборы, credentials) |
| **HOST_SET** | Один набор хостов |
| **HOST** | Один хост |

**Приоритет:** более специфичный scope не перекрывает менее специфичный,
они **складываются** как union. Пример:

```text
admin_a:
  ADMIN @ DOMAIN a.local
  VIEWER @ DOMAIN b.local
```

В `a.local` — полный CRUD. В `b.local` — только чтение.

### Как scope применяется

- **Firewall** применяется только к хостам в scope.
- **Deployment** можно создать только на хосты в scope.
- **Credentials** видны только для объектов в scope.
- **ConfigProfile / Repository / Certificate** — глобальные сущности,
  редактировать их может любой ADMIN (в будущем — привяжем к домену).

## Иерархия управления ролями

Кто кем может управлять:

| Менеджер | Может выдавать | Где |
| --- | --- | --- |
| SUPERVISOR | ADMIN, AUDITOR, OPERATOR, VIEWER | В любом scope (GLOBAL) |
| ADMIN | OPERATOR, VIEWER | В своём домене / наборе / хосте |
| ADMIN | AUDITOR | **нет** (только SUPERVISOR) |
| ADMIN | ADMIN | **нет** |
| SUPERVISOR | SUPERVISOR | **нет** (правило ≥2, двухстороннее подтверждение) |

Реализация — `apps.access.permissions.can_manage_role()`.

## Способы выдачи

### Инвайт (основной)

Через UI: SUPERVISOR/ADMIN создаёт приглашение:

```text
Email: ivan@company.local
Роль:  ADMIN
Scope: DOMAIN a.local
Срок:  до 2027-01-01 (опционально)
```

Пользователь получает письмо, переходит по ссылке, регистрируется
(задаёт логин + пароль), инвайт закрывается.

Инвайты для **SUPERVISOR** и **ADMIN** требуют **двухстороннего
подтверждения**: их должен подтвердить второй SUPERVISOR, отличный
от инициатора.

### Прямое назначение (для существующих)

Если пользователь уже зарегистрирован, ADMIN/SUPERVISOR может
назначить ему роль напрямую:

```text
UI: /access/roles/assign/
```

Для ADMIN/AUDITOR — обязательны 2 апрувера. Для OPERATOR/VIEWER —
достаточно одного.

### Через AD (не реализовано)

Синхронизация с AD используется только для инвентаря (`Host`), не для
ролей. Роли всегда выдаются через инвайт или прямое назначение.

## Совмещение ролей

Один пользователь может иметь несколько ролей **и несколько scope**:

```text
ivan:
  SUPERVISOR @ GLOBAL
  ADMIN      @ DOMAIN a.local
  OPERATOR   @ HOST_SET web-servers
```

В результате:

- глобально — SUPERVISOR (чтение всего, приглашение ADMIN);
- в `a.local` — ADMIN (CRUD домена);
- в `web-servers` — OPERATOR (создание деплоев).

**Правило безопасности:** глобальная роль SUPERVISOR **не даёт**
write-прав, даже если совмещена с ADMIN другого домена. В каждом
домене права определяются назначением в этом домене.

## Матрица ролей × действий

Полная матрица — в `apps/access/permissions.py:CAN_MANAGE` и
`AAL_REQUIREMENTS_BY_ACTION`. Сводная таблица:

| Действие | SUPERVISOR | ADMIN | OPERATOR | AUDITOR | VIEWER |
| --- | --- | --- | --- | --- | --- |
| Видеть все домены | ✓ | — | — | — | — |
| Видеть свой домен | ✓ | ✓ | ✓ | ✓ | ✓ |
| Создать/изменить домен | — | ✓ | — | — | — |
| Создать/изменить хост | — | ✓ | — | — | — |
| Создать/изменить профиль | — | ✓ | — | — | — |
| Смотреть credentials (метаданные) | ✓ | ✓ | — | — | — |
| Менять credentials | — | ✓ (AAL3) | — | — | — |
| Читать значения секретов | — (только метаданные) | ✓ (owner) | — | — | — |
| Создать deployment | — | ✓ | ✓ | — | — |
| Отменить deployment | — | ✓ | ✓ | — | — |
| Пригласить OPERATOR/VIEWER | ✓ | ✓ | — | — | — |
| Пригласить ADMIN | ✓ (2 подписи) | — | — | — | — |
| Пригласить AUDITOR | ✓ (2 подписи) | — | — | — | — |
| Отозвать роль | ✓ | ✓ (OPERATOR/VIEWER) | — | — | — |
| Смотреть audit | ✓ | ✓ (свой домен) | — | ✓ | — |
| Смотреть отчёты hardening | ✓ | ✓ | ✓ | ✓ | ✓ |

| Менять high-security mode | SUPERVISOR (AAL3, 2 подписи) | — | — | — | — |

## Базовые инварианты

Реализованы в `apps/access/checks.py`:

1. **Всегда ≥2 SUPERVISOR'а.** Никто не может отозвать последнего
   SUPERVISOR'а или понизить его, если после этого останется < 2.

2. **Нельзя понизить себя.** SUPERVISOR не может отозвать свою
   роль SUPERVISOR или изменить свой scope.

3. **ADMIN не управляет AUDITOR'ом и другим ADMIN'ом.** Только
   SUPERVISOR.

4. **Инвайты SUPERVISOR/ADMIN — двухсторонние.** Один человек не
   может единолично выдать такую роль.

5. **Нельзя изменять audit.** `AuditLog` и `AuthAuditLog` — append-only
   (см. `docs/tamper.md`).

## Смена роли «на лету»

Если роль пользователя изменилась во время активной сессии:

1. Создаётся `RoleChangeNotice` для пользователя.
2. При следующем запросе middleware редиректит его на
   `/access/roles-changed/`.
3. Пользователь видит, что изменилось, и должен подтвердить («Я ознакомлен,
   выйти»).
4. После подтверждения — сессия закрывается. При следующем входе вступят
   в силу новые права.

Такой подход даёт **немедленное** применение новых прав (не ждём
истечения сессии) и **гарантированное** уведомление.

## Access review

Раз в 90 дней celery создаёт прогон `AccessReviewRun`:

- для каждой активной `RoleAssignment` создаётся `AccessReviewItem`;
- SUPERVISOR'ы видят список и подтверждают/отзывают каждую роль;
- по истечении `due_by` (14 дней по умолчанию) — item помечается
  `expired`, но роль не отзывается автоматически.

Ручной запуск:

```bash
manage.py access_review start
```

Просмотр:

```bash
manage.py access_review list
manage.py access_review show <run_id>
```

UI: `/access/access-review/`.

## Приглашение «всех, кого нет»

Если у вас есть список сотрудников (например, из AD), но их нет
в Django — используйте импорт:

```python
# В будущем — bulk-import через CSV или LDAP-синк.
# Сейчас — только индивидуальные инвайты.
```

Импорт всех AD-учёток **не делается** осознанно (см. `docs/auth.md`).
